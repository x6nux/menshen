# Menshen 门神

Telegram 群组反广告 bot。群消息经 AI 两级判定，按「用户资历 × 置信度」
自动删除 / 禁言，并把处置结果连同一键纠错按钮推给管理员。

> 门神贴在门上挡邪祟。这个项目的两道主防线也都在门口 —— 冷判定拦进群、
> 联合封禁拦全平台，宁可不让他进来，也不等他进来发完再删。

纯 Go，无 CGO，单文件二进制 + 一个 SQLite 库。多租户：一个进程服务
任意多个 bot，各归各的管理员。

## 它怎么判

```
群消息 → 守门（总开关/群白名单/豁免）→ 留底 → 护栏（去重/频率）
       → systemone 主判（带置信度的结构化决策）
       → 置信度不足才转大模型复判
       → 处置矩阵 → 处置 + 告警 + 流水
```

两级判定共用同一份送检载荷，看到的信息完全一致。**判定失败一律放行** ——
反过来会在上游抖动时清空整个群聊。

网络抖动与 5xx/429 会自动重试（最多 5 次，指数退避，逐个轮换上游）；
4xx 是配置问题，重试多少次都一样，直接失败。主判模型报错时不空等，
当场落到复判模型 —— 有一个能答上来就不该放行。

处置矩阵（阈值均可调）：

| 置信度 | 新人 | 老人 |
|---|---|---|
| ≥ 90% | 删除 + 禁言 + 告警 | 删除 + 告警 |
| 75% ~ 90% | 删除 + 告警 | 仅告警 |
| < 75% | 不处置 | 不处置 |

新人 = 进群 < 72 小时 **或** 群内发言 < 10 条（潜伏号）。
老人永远不自动禁言：误伤一个长期成员的社交代价远大于漏一条广告，
告警里给管理员一键补刀的按钮就够了。

**演练模式按群设**：判定照跑、开销照花，但不删不禁言，只报告「本应执行
什么」。新加的群先演练、老群已正式是最常见的需求，所以它落在每个群上
而不是全局一刀切。

进群时还有一道**冷判定**（默认关）：本地预筛筛出昵称或简介里带引流话术
的账号，只把这些送 AI 判画像，命中即限制发言并给出具体原因。被限制的人
可以在群里点按钮、私聊完成人机验证后自助申请复核 —— 改对了当场解除。

## 闭环学习

管理员在告警上点「↩️ 误判」，该样本进反例池；确认命中的进正例池。
积累够数后自动总结成一段形态摘要，回注入此后每一条消息的判定。
摘要可在面板上直接编辑 —— AI 写歪时不必等下一轮覆盖。

摘要会乘以每一条群消息的成本，面板上明码标价了它折合多少 token。

## 快速开始

```bash
CGO_ENABLED=0 go build -o menshen .
cp config.example.yaml config.yaml   # 填 bot_token 与 admin_ids
./menshen -config config.yaml
```

然后私聊 bot 发 `/start`：

1. **🔌 上游渠道** — 加至少一个 AI 上游（base_url + api_key）
2. **🤖 模型定价** — 录入模型名与单价（只用于把开销折算成钱）
3. **⚙️ 全局设置** — 选默认判定模型，打开总开关
4. **🤖 我的机器人** — 添加生效群 chat_id（可为单个 bot 覆盖模型）
5. 把 bot 拉进群并**设为管理员**（删除消息 + 封禁用户权限）
6. 观察几天演练结果，校准阈值后切正式模式

## 多租户

主管理员掌握上游、模型与联合封禁 —— 也就是掌握钱。他可以添加**次级
管理员**，次管各自接入自己的 bot、管自己那些 bot 在各群的行为与判定阈值。

| | 主管理员 | 次级管理员 |
|---|---|---|
| 上游渠道 / 模型定价 | ✅ | ❌ |
| 判定模型 | 全局默认 + 为单个 bot 覆盖 | ❌ 由主管配 |
| 接入 bot | 全部 | 只限自己名下（配额 `max_bots_per_admin`） |
| 群配置 / 阈值 / 流水 | 全部 | 只限自己 bot 名下 |
| 联合封禁开关与名单 | ✅ | ❌ |

主管理员名单只存在于配置文件里，不进数据库 —— 面板上删不掉它。

**接入一个 bot**：面板上点「➕ 接入新机器人」，把 BotFather 给的 token 发过来
就行。本服务会自动验证它、取回 bot 的身份、起实例并注册回调地址，全过程
在一条消息里实时汇报。你发的那条含 token 的消息**会被自动删掉** —— token
等同于该 bot 的完整控制权，不该留在聊天记录里。

**联合封禁**（默认关）：一处判到最高档或被人工标记，全平台所有接入群
一起封，并拦在进群那一刻。解除时走 `only_if_banned`，不会把没被封的人
反而踢出群。

## 两种接入方式

### 长轮询

配置里填 `bot_token` 就是这个模式，不需要公网地址。启动时会先
`deleteWebhook` —— getUpdates 与 webhook 互斥，库里留着上次的 webhook
会让 getUpdates 一直拿 409，而表现为「一条消息都收不到」。

### Webhook（多 bot 接入）

配置里填 `public_url` 即切换到这个模式。它是回调地址的**前缀**，
可以带任意层子路径：

```yaml
public_url: "https://ad.example.com/tg"
# → 回调地址 https://ad.example.com/tg/<BOT_TOKEN>/webhook
```

已注册的每个 bot 由本进程自动 `setWebhook`，不必手工调用。

- 路径里的 token 本身就是凭证，与官方 `/bot<TOKEN>/method` 的认证模型一致
  —— 知道 token 的人本来就能直接控制那个 bot，伪造推送并不会多出任何权限
- **接入是注册制**：token 必须先在面板上登记过（绑定 owner），
  没登记的一律 401，连 `getMe` 都不会发。`getMe` 验真在登记时做一次
- 路径解析锚在 token 自身的格式上，所以 `/bot<TOKEN>`（官方形态）
  与反代再套几层子路径都认得出来
- 每个 bot 的更新由**一个** worker 串行消费，与长轮询语义完全一致
- `GET /healthz` 供反代探活

**多 bot 必须用 webhook。** 长轮询模式下接入子 bot 会被直接拒绝：getUpdates
要为每个 bot 各开一条长连接，而 Telegram 的限速同时按 bot 和按出口 IP 算 ——
几个 bot 一起轮询会互相挤掉配额，表现是所有 bot 一起变慢、一起丢更新，
且没有任何一条日志指向真正的原因。

已经接入的子 bot 在切回长轮询后不会启动（记录留着，面板上标为「已启用但
没有在运行」），改回 webhook 重启即自动恢复。

反代示例（nginx）：

```nginx
location / {
    proxy_pass http://127.0.0.1:8081;
    proxy_set_header Host $host;
}
```

监听地址默认只听回环。这个端口上的请求等同于「以 bot 身份收发消息」，
不要直接暴露到公网。

## 群内命令

`/ad` —— 复查某人是否在发广告。回复对方的消息发 `/ad`，或直接
`/ad <user_id>`。它把该用户在本群的**全部留底**一次性交给两个模型，
两方结论互相印证后走同一套处置矩阵。

对所有人开放：它不直接封禁，而群成员往往比管理员更早发现广告。
它同时是花钱与骚扰入口，靠 `antiad_cmd_rpm` 按发起人限频。

`/adb` —— **人工直接标记为广告**。回复对方的消息发 `/adb`，不经过 AI，
直接按最高档处置（删除 + 禁言），并进联合封禁名单。

限**群管理员及以上**（群管 / bot 归属人 / 主管理员）：它绕过判定直接
删人禁言，对全群开放等于把删消息的权力交给任何人。非授权者**静默忽略**
—— 回一句「你没有权限」等于告诉刷屏的人这条命令存在、值得去试。

标记结果进正例池，是质量最高的训练样本，形态摘要下一轮就能学到。

## ⚠️ 三个从代码里看不出来的坑

1. **bot 不是群管理员 = 一条普通群消息都收不到。**
   Telegram 的 privacy mode 默认只把命令和回复推给 bot。此时面板一切正常、
   日志干净、什么都没判。兜底是反广告面板上每个生效群后面的自检标记
   （✅ 权限正常 / ⚠️ bot 非管理员）。
   privacy 是在 bot 入群时定下的：在 BotFather 里改完必须**把 bot 移出群
   再重新加**。

2. **`allowed_updates` 一旦显式声明，Telegram 的默认清单就整体失效。**
   所以 `message` / `callback_query` 也必须原样列在里面，删掉哪个哪个就
   彻底收不到，而 getUpdates / setWebhook 都不会因此报任何错。

3. **判定链路有四个前置条件，缺任何一个都表现为「一条都没拦到」而不报错。**
   主菜单会逐条点名还缺什么，别忽略那段提示。

## 成本

**每条群消息都送检**，这是设计如此，不做抽样。面板上「近 24 小时」那行
实时摆着送检数与折算开销 —— 这是这个功能最大的风险点，所以放在最显眼处。

护栏（都可调）：窗口内重复文本去重、每群每分钟送检上限、同一人告警节流、
`/ad` 按人限频。它们只堵滥用，不改「每条都判」的设计。

## 数据

| 表 | 内容 |
|---|---|
| `antiad_log` | 判定账本：置信度、处置、开销。**只记判过的** |
| `group_messages` | 群消息全量留底，供 `/ad` 复查。被护栏拦下的、豁免者发的都在这里 |
| `group_members` | 群成员画像，「新人 / 老人」分档的唯一来源 |
| `bots` / `bot_chats` / `bot_settings` | 接入的 bot、它的生效群与每群行为、per-bot 阈值覆盖 |
| `admins` | 次级管理员。主管理员**不在这里**，他只存在于配置文件 |
| `gban` / `join_mutes` | 联合封禁名单、进群冷判定的限制记录 |

`group_members` 与 `group_messages` 不带 `bot_id`：同一个群的同一个人
本就该共用一份画像，哪怕两个 bot 都在这个群。

三者按「记录保留天数」一起清理（有命中史的画像行保留 —— 那是风控证据）。
库里有上游 api_key 明文，建议 `chmod 600 data.db`。
